# AI 助手目标主机选择需求说明

本文定义「AI 助手 → 目标机器」下拉里**哪些机器可以出现**，以及页面必须如何解释
这份筛选。它是 `backend/app/ai_scope.py`、`backend/app/ai.py`（`resolve_host`）与
`src/pages/AiAssistant.tsx` 的行为依据；三者必须保持一致，不能出现「页面列出来了、
后端却拒绝」或反过来的情况。

## 1. 目的

AI 助手不是只读报表：它会登录目标主机执行命令，并可通过 QEMU Guest Agent 进入
虚拟机内部取证。目标选错一台，后果不是「看错一页」，而是在另一台机器上跑了命令。
因此候选清单按「这一轮确实做得到」计算，而不是按「平台里有这台机器」计算。

**核心规则：五个条件为「与」关系。必须同时满足全部五项；任一条件不满足，该主机
即被排除，不进入候选，也不允许绕过页面直接发起排查。**

## 2. 适用范围

| 场景 | 是否适用 |
| --- | --- |
| AI 助手页「目标机器」下拉 | 是 |
| `GET /api/ai/targets` 返回的候选 | 是 |
| `POST /api/ai/inspect`、会话创建、会话续聊时对 `host_id` 的准入 | 是（`resolve_host` 复核） |
| 虚拟机内取证的「目标虚拟机」租约 | 独立判定（运行中 + Guest Agent）；本文的五条件针对「目标机器」下拉 |
| 面板本机（`local`） | 不适用：本身就被排除，不能作为 AI 目标 |
| 纯虚拟机会话（没有关联受管主机、只靠租约） | 不经过「目标机器」下拉；由租约侧的运行中 + Agent 校验兜底 |

## 3. 术语与数据来源

| 术语 | 含义 | 数据来源 |
| --- | --- | --- |
| 受管主机 | 在「SSH 安全 → 受管主机」里登记、且当前用户可见的服务器 | `baseline.targets()` + `hostscope.allowed_host_ids()` |
| 安全纳管 | 该服务器已登记为受管主机，平台持有可用凭据；面板下发的机器由 cloud-init 注入统一密钥后自动登记 | `ssh_hosts` / `sshremote` |
| 开机运行 | PVE 报告虚拟机状态为 `running` | `GET /nodes/{node}/qemu/{vmid}/status/current` |
| Guest Agent 正常 | 客户机内 `qemu-guest-agent` 已安装、已启动，且虚拟机配置里 `agent` 已启用，`agent/ping` 在超时内应答 | `POST /nodes/{node}/qemu/{vmid}/agent/ping` |
| cloud-init 正常 | 虚拟机挂了 cloud-init 盘（config 中存在含 `cloudinit` 的卷），且配置了登录身份（`ciuser` / `sshkeys` / `cipassword` 至少一项） | `GET /nodes/{node}/qemu/{vmid}/config` |
| 虚拟机（VM） | PVE 资源类型为 `qemu`，且受管主机记录带 `node` + `vmid`；不是 LXC 容器、不是模板 | PVE 状态接口 + 受管主机记录 |

## 4. 准入条件（全部为「与」）

### C1 处于开机运行状态

- **判定标准**：PVE 的状态接口返回 `status == "running"`。
- **视为不满足**：`stopped`、`paused`、`suspended`、`unknown`、空值，以及读取状态
  失败（超时、401/403、5xx、连接不可达）。
- **边界**：
  - 迁移、备份、锁机等操作期间状态仍可能是 `running`；只要 Agent 仍应答即可通过。
    迁移过程中 Agent 短暂掉线会按 C5 排除，迁移结束后重新出现。
  - 状态读取超时为 3 秒；超时按「读不到」处理（`unreachable`），不是「没运行」。
  - PVE 返回 404 表示这个 VMID 不存在或不是 QEMU，按 C5 处理（`not_vm`）。

### C2 已被安全纳管

- **判定标准**：该服务器存在于「SSH 安全 → 受管主机」且 `enabled = 1`，并在当前
  用户的可见范围内（`hostscope` 过滤之后）。
- **视为不满足**：未登记、已停用、被当前用户的数据边界排除、面板本机（`local`）。
- **边界**：
  - 手工添加的受管主机**不因来源被排除**；只要它绑定了 `node` + `vmid` 并通过其余
    四项，同样可以作为目标。
  - `hostscope` 排除发生在准入判定之前，因此这类机器**不计入**「被排除」统计——
    用户本来就看不到它们，统计里出现数量会泄露资产规模。
  - 凭据存在但不可用（密码错误、密钥被轮换）不在本条件判定；它会在实际登录/探测
    阶段表现为后续条件失败或执行报错。

### C3 Guest Agent 运行正常

- **判定标准**：`agent/ping` 在 3 秒内成功返回。
- **视为不满足**：超时、连接被拒、Agent 未安装、Agent 服务未启动、虚拟机配置未
  启用 `agent`、PVE 权限不足。
- **边界**：
  - 只 ping，不执行任何命令；这是「进得去」最便宜的证据。
  - Agent 应答但客户机内 `cloud-init` 本次开机失败，本条件仍视为通过；运行时状态
    属于具体动作的校验范围（见 §8）。
  - 没有 Agent 时**不降级**为「仅主机命令」继续本次排查——目标一旦选定，就不该在
    执行中途悄悄换一种能力模型。页面在筛选阶段就会排除它。

### C4 cloud-init 运行正常

- **判定标准**：虚拟机配置中存在 cloud-init 盘，且配置了登录身份：`ciuser` /
  `sshkeys` / `cipassword` 至少一项非空。
- **视为不满足**：没有 cloud-init 盘；三种登录身份字段全为空；配置读取失败（按
  `unreachable` 处理，不误报为「没配置」）。
- **边界**：
  - 这里判的是「配置完整」，不是「本次开机已经跑完」。批量列清单时逐台进入客户机
    执行 `cloud-init status` 代价过高，且 Agent 已在线说明客户机可执行命令；需要
    运行时确认的动作，在执行时自行验证。
  - **不要求必须写 `ciuser`**：只用 `sshkeys` 或只用 `cipassword` 也是完整的
    cloud-init 登录配置，不能因为字段名不同就误判。
  - Windows 客户机使用 Cloudbase-Init，判定口径相同：有 cloud-init 类 config drive
    + 登录身份即可，不按 Linux 专有字段判断。
  - 模板、克隆源没有 cloud-init 盘时按本条件排除。

### C5 是虚拟机（VM）

- **判定标准**：受管主机记录带 `node` 与 `vmid`，且该 VMID 在 PVE 上是 QEMU 虚拟机。
- **视为不满足**：`node` 或 `vmid` 为空；VMID 指向 LXC 容器；VMID 已不存在；是模板。
- **边界**：
  - 手工主机没有绑定虚拟机 → 排除（`not_vm`）。这是「目标必须是 VM」的直接结果。
  - 同一 `node` + `vmid` 可能存在于多条 PVE 连接：优先使用受管主机记录里的
    `conn_id`；`conn_id` 为空时退回当前连接，可能读不到而按 `unreachable` 排除。
  - VMID 被删除后重建：30 秒缓存内可能短暂沿用旧结论；发起排查时会重新判定，
    配置/Agent 不匹配就会被拦下。

## 5. 筛选关系与执行顺序

1. 先由 `hostscope` 收窄到当前用户可见的受管主机，再由 `ai.ai_targets` 剔除面板本机。
2. 对剩余主机逐台执行 C5 → C1 → C4 → C3。C2 已在上一步完成。
3. **全部条件通过才进入候选**；任一失败立即排除，不保留「部分可用」状态。
4. 判定顺序只影响成本与原因归类，不改变「与」的语义。
5. 结果分两部分返回：
   - `hosts`：可用主机；
   - `excluded`：按原因聚合的**数量**（`not_vm` / `stopped` / `cloudinit` / `agent` /
     `unreachable`），**不返回主机名**。
6. 失败一律 fail-closed（读了算不出来就排除），不允许「先列出来、点进去再报错」。

## 6. 性能与新鲜度

| 项 | 取值 | 说明 |
| --- | --- | --- |
| 单台上游超时 | 状态 3s / 配置 3s / Agent ping 3s | 避免一台客户机拖住整张清单 |
| 并发探测 | 8 台 | 既不让页面等十几秒，也不在 PVE 上瞬间打出一串请求 |
| 结果缓存 | 30s | 只影响候选清单的新鲜度；发起排查时会重新判定 |
| 重新判定 | 每次 `resolve_host` | 覆盖「列表加载后机器被关机 / Agent 掉线」的时间差 |

缓存按 `(conn_id, node, vmid)` 键控，不按主机名或用户；没有 `node` / `vmid` 的
主机在本地即可判定为 `not_vm`，不进入缓存。

## 7. 页面说明要求

页面必须让用户看懂两件事：**为什么列表里只有这些机器**，以及**少了的那几台缺什么**。
不能只把下拉做短，让用户去猜。

### 7.1 目标选择器提示

- 位置：「目标机器」字段的 hint。
- 中文文案：
  > 只列同时满足五项条件的机器：运行中、已安全纳管、Guest Agent 正常、cloud-init
  > 正常、是虚拟机。缺任意一项都不会出现在这里。
- 英文文案：
  > Only machines meeting all five conditions are listed: running, securely managed,
  > Guest Agent healthy, cloud-init healthy, and a VM. Any one missing and it will not
  > appear here.

### 7.2 未选择目标时的说明

- 位置：页面上方的提示条。
- 必须说明：
  1. 目标只能由用户当场指定，面板不默认选一台（查错机器比多点一次严重得多）；
  2. 五项条件是「与」关系，任一不满足都无法完成排查；
  3. 因此候选只包含同时满足五项的机器。
- 中文文案：
  > AI 会登录到这台机器上读日志、跑命令，所以目标只能由你当场指定 —— 面板不替你
  > 默认选一台，查错机器比多点一次严重得多。候选只包含同时满足「运行中 + 已安全
  > 纳管 + Guest Agent 正常 + cloud-init 正常 + 虚拟机」的机器：这五项是「与」的
  > 关系，任一不满足就做不成这一轮排查，因此直接排除。

### 7.3 列表被排除过主机时的说明

- 位置：「目标与模型」区块内的提示条，仅当 `excluded.total > 0` 时出现。
- 必须包含：
  1. 限制的**必要原因**：AI 要登录执行命令，并通过 Guest Agent 进虚拟机取证；
     两条链路都要求「运行中的虚拟机 + Agent 在线」；cloud-init 负责下发登录凭据
     与身份配置，缺了平台无法确认归属与访问方式。
  2. 「与」关系的结论：任一不满足即无法完成排查，所以不列出；列出做不了的机器
     只会让人签完授权才发现第一步就失败。
  3. 被排除的**数量与原因分类**，不列主机名。
- 中文文案（正文）：
  > AI 要登录目标主机执行命令，并通过 Guest Agent 进入虚拟机取证。这两条链路都
  > 要求机器是「正在运行的虚拟机」且 Guest Agent 在线；cloud-init 负责下发登录
  > 凭据与身份配置，缺了它平台无法确认这台机器的归属与访问方式。五项条件是与的
  > 关系，任一不满足都无法完成排查，所以不列出来 —— 让一台做不了的机器出现在
  > 下拉里，只会让人签完授权才发现第一步就失败。
- 计数行：`另有 {n} 台受管主机未列出：{原因列表}`，原因按
  `不是虚拟机 / 未开机运行 / cloud-init 不完整 / Guest Agent 未响应 / 状态读取失败`
  聚合，只显示计数。

### 7.4 没有可用目标时

- 若用户确实没有任何受管主机：沿用「还没有受管主机」提示，引导去「SSH 安全 →
  受管主机」登记。
- 若受管主机存在但全部不满足条件：显示「暂无可排查的主机」，并给出可操作的修复
  方向：
  > 受管主机里没有一台同时满足五项条件（运行中、已安全纳管、Guest Agent 正常、
  > cloud-init 正常、虚拟机）。请先启动目标虚拟机，确认客户机内已安装并运行
  > qemu-guest-agent、虚拟机配置里已启用 agent，且 cloud-init 盘与登录用户配置
  > 完整。

### 7.5 已选目标在发起时失效

- 不静默换一台，也不回退到「仅主机命令」。
- 返回明确原因，例如：
  > 目标主机「web1」当前不满足 AI 排查条件：Guest Agent 没有响应。请先把它恢复
  > 到可用状态，再重新发起。
- 原因必须与 C1–C5 一一对应，不能统一成「不可用」。

## 8. 边界情况处理规则

| 场景 | 处理 | 用户看到 |
| --- | --- | --- |
| PVE 整体不可达 | 所有主机按 `unreachable` 排除 | 「暂无可排查的主机」+ 状态读取失败计数 |
| Token 缺少 VM.Audit / Agent 权限 | 同上 | 同上；不误报为「未配置 cloud-init」 |
| 虚拟机 `stopped` / `paused` / `suspended` | 排除（`stopped`） | 未开机运行计数 +1 |
| 虚拟机是模板 | 不满足 C1/C5，排除 | 不单独提示模板 |
| VMID 指向 LXC | 排除（`not_vm`） | 不是虚拟机计数 +1 |
| 手工主机未绑定 `node/vmid` | 排除（`not_vm`） | 不是虚拟机计数 +1 |
| 手工主机绑定了 VM 且四项通过 | **允许**；不以 `origin=panel` 为门槛 | 正常出现在候选 |
| 没有 cloud-init 盘 / `ciuser` 为空 | 排除（`cloudinit`） | cloud-init 不完整计数 +1 |
| cloud-init 配置完整但本次开机执行失败 | 候选阶段通过；具体动作在客户机内验证并报错 | 动作级错误，不改变候选 |
| Agent 未安装 / 未启动 / `agent=0` | 排除（`agent`） | Guest Agent 未响应计数 +1 |
| Agent 应答慢于 3 秒 | 排除（`agent`）；30 秒后可重试 | 同上 |
| 虚拟机迁移中 Agent 短暂掉线 | 按当前探测结果排除 | 迁移结束后重新加载即可出现 |
| 受管主机被停用 | 不进入候选（C2） | 不计入排除统计 |
| 用户失去该主机可见范围 | 不进入候选（C2） | 不计入排除统计 |
| 列表加载后机器被关机 | 发起时重新判定并拒绝 | 明确原因 + 重试指引 |
| 30 秒缓存内状态变化 | 候选可能短暂滞后；发起时复核 | 最坏 30 秒后列表更新 |
| 多条 PVE 存在同名 node/vmid | 优先 `conn_id`；为空时可能 `unreachable` | 状态读取失败计数 +1 |

## 9. 验收标准

1. **与关系**：构造五台机器，分别只缺 C1、C2、C3、C4、C5，均不出现在 `hosts`
   里；五项全满足的那台必须出现。
2. **候选与准入一致**：直接从下拉拿不到的 `host_id` 调用
   `POST /api/ai/inspect` 或创建会话，返回 400/明确原因，而不是开始执行命令。
3. **失败关闭**：PVE 超时、403、404 分别归入 `unreachable` / `unreachable` /
   `not_vm`，不得放行。
4. **计数不泄名**：`excluded` 只含数量与原因键，不含 `id` / `name` / `address`。
5. **页面解释**：未选择目标时能看到五条件与「与」关系；存在被排除主机时能看到
   原因计数；全部排除时能看到修复指引。
6. **无默认值**：页面不会自动选中第一台；从其他页面带 `host_id` 进来时，若该机器
   不在候选中，提示用户重新选择，而不是硬塞进下拉。
7. **刷新时效**：关机后最迟 30 秒从候选消失；重新开机并恢复 Agent 后最迟 30 秒
   重新出现（发起时另有实时复核）。

## 10. 非目标

- 不在候选阶段逐台进入客户机执行 `cloud-init status`。运行时状态由具体动作校验，
  避免为了列一张清单在几十台机器里跑命令。
- 不为「仅主机命令」保留一条绕过五条件的旁路。目标一旦不能完成本轮排查，就在
  候选阶段排除，而不是执行到一半降级。
- 不把被排除主机的名称下发给前端；原因计数已足够解释列表变短。

## 11. 实现位置

| 层 | 文件 | 职责 |
| --- | --- | --- |
| 准入判定 | `backend/app/ai_scope.py` | 五条件与运算、原因码、超时、并发、30s 缓存 |
| 候选清单 | `backend/app/routers/ai.py` → `GET /targets` | 先 `hostscope` + `ai_targets`，再 `evaluate_hosts`，返回 `hosts` 与 `excluded` |
| 发起复核 | `backend/app/ai.py` → `resolve_host` | 候选与发起共用同一规则，拒绝时给出具体原因 |
| 页面 | `src/pages/AiAssistant.tsx` + `src/i18n/locales/{zh-CN,en}.ai.ts` | 五条件提示、排除计数、无可用目标指引、失效原因 |
